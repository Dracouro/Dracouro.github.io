交互系统

看到什么、能抓什么、左键按下去到底发生什么 —— 以及为什么同一个滚轮在两种状态下语义完全不同。

进行中C++蓝图

为什么不做进角色里

一开始交互逻辑是写在 BP_Farmer 里的 —— 射线检测、找可交互物、显示提示、执行动作。 写到第四个可交互物的时候问题就来了：机器要交互、载具要交互、作物也要交互， 难道每个都往角色里加分支？

于是拆成两层：

  • 接口管「能不能」 —— 一个物品实现 BPI_Interactable 就能被看向， 实现 BPI_Grabbable 就能被抓。它不需要知道谁在看它、谁在抓它。
  • 组件管「怎么判」 —— AC_InteractionManager 挂在玩家身上， 统一做射线、高亮、状态判定与分支派发。

这套拆分是后来所有「冲突类 bug」的解药：两种交互打架的时候， 要改的永远是分派那一处，而不是散在十几个物品蓝图里的判断。

三个接口，职责严格分开

接口 提供什么 谁在用
BPI_Interactable LookAt（看向）、OnInteract、OnGrab 悬停高亮与交互入口；BP_ItemMaster 实现它
BPI_Grabbable CanBeGrabbed、GetGrabbablePrimitive、GetItemRowName 抓取判定与「这东西对应 DT_Items 哪一行」
UItemIdentityInterface（C++） GetItemIdentityRowName、GetHotbarSlotIndex 存档与快捷栏：把 UObject 指针还原成行名

⚠️ LookAt 挂在 BPI_Interactable 上，不在 BPI_Grabbable 上。 这两条线是正交的：看向高亮走一套，抓取与拼装吸附走另一套。 曾经想「反正都是交互，合成一个接口算了」，结果删一个就会让 AC_InteractionManager / AC_HighLightComponent 的动态 Cast 断链 —— 高亮和抓取是两种不同的「能」，别合并。

左键到底干了什么

整个游戏只有一个左键入口，它内部按「这东西有没有装配记录」分成两条路：

TryGrab(射线命中的 Actor)
  │
  ├─ IsInteractionBlocked(Target)?           ← 统一阻断门，先问
  │     ├ 花盆：CurrentPlantCount > 0 → 拒绝
  │     └ 化学器具：所属反应状态 == Processing → 拒绝
  │
  └─ GetGrabbablePrimitive → Cast<MeshComponent>
        └ GetRecordConstraint(Component).Find?
              ├ true  → GrabNewComponent / ReleaseItem
              │          物理抓取：世界里的物体被手柄拎起来，**不销毁、不进背包**
              └ false → AddItemByID + 销毁世界 Actor
                         普通拾取：场景里的东西消失，背包 +1，手上有模型

这条分岔极其容易踩错。固化出来的产物一开始没有登记装配记录， 于是明明是个装配体，点它却走了「拾取」分支 —— 物体从场景里消失、 背包多了一坨东西、再也放不回地上。修法是在固化时补注册 （见拼装合成的 RegisterSynthesizedResult）。 反过来说，种子、肥料这类单件本来就不该有记录， 所以它们的「收进背包」路径完全不受影响 —— 这正是把判据放在 「有没有记录」而不是「是什么类型」上的好处。

统一阻断门

/**
 * 这个 Actor 现在必须拒绝点击拾取 / 抓取吗？
 *
 * 目前覆盖：
 *  1. 种了活植株的可种植表面（花盆），要移除植株才能动它；
 *  2. 正在 Processing 的化学反应所属的器具，要等产物出来。
 *
 * 纯查询，用作 TryGrab 开头唯一的提前返回。
 */
UFUNCTION(BlueprintPure, Category = "Interaction")
static bool IsInteractionBlocked(AActor* Target);

它的价值在于**「不可交互」这件事只写一遍**。以后再加一种「暂时不能动的状态」 （比如装置过热、门锁着），只往这个函数里加一条 —— 蓝图零改动。 注意它只挡拾取/抓取入口，不挡高亮：玩家仍然应该看得见这个物体、知道它存在， 只是现在动不了，而不是「眼前一片空白」。

碰撞契约：两种交互必须正交

场景物品（BP_ItemMaster 的子类）的 StaticMesh 必须用命名碰撞预设 AssemblyItem：

设置 值 为什么
ObjectType PhysicsBody 拼装吸附用 SphereOverlapComponents(ObjectTypeQuery4=PhysicsBody) 扫零件，不设就扫不到
CustomResponses RayTracing(GameTraceChannel1) = Block 悬停高亮与左键拾取都打这条通道，它的默认值是 Ignore

这两条分别服务两个系统，缺一个就会出现「能抓但吸附不到」或者 「能吸附但点不中」这种单边故障 —— 排查时先看这条。

⚠️ 另外，不要内联写 Custom 碰撞。临时禁用重叠用的 DisableOverlapComponentCollision 会先换成 overlapall 再按预设名恢复， 对内联的 Custom 恢复是无效的 —— 装配体会直接掉出场景。

滚轮：一个键，两种语义（这层是踩出来的）

物理手柄在游戏里其实扛着两种完全不同的东西：

  1. 世界里的物体 —— 合并体、固化产物、散落的可抓件；
  2. 手部模型 —— ItemInHand 生成的手上那件东西， 它也是走同一套物理手柄纯粹为了让手感“晃”起来。

问题就在这儿：IA_GrapDistance（推拉抓取物）和 IA_HotbarScroll（切快捷栏） 都映射在 MouseWheelAxis 上，于是每一格滚轮同时做两件事。正确的语义是：

手里正抓着 滚轮应该做的事
世界物体 把物体推远 / 拉近
手部模型（或空手） 切换快捷栏，并把下一格的模型换到手上

判定被收敛成两个查询函数，避免各处自己判断：

/** 玩家物理手柄此刻抓的是"世界物体"吗？（手部模型不算） */
static bool IsGrabbingWorldObjectOnPawn(const AActor* Pawn);

/** 手部模型的唯一事实源：UHotbarManagerComponent::EquippedHandActor */
static AActor* ResolveHandModelActor(const AActor* Pawn);

顺带修掉的两个真实缺陷：

  • 手上的模型换不掉。 滚轮切栏原本读 UHotbarManagerComponent.HotbarItems， 但工程里没有任何地方往这个数组写过东西（只有 UI 在读它）， 所以切栏永远是「先清空手上、再装上空的」= 模型消失。 现在滚轮复用数字键那条路（StepHotbarEquip 走 BP_Farmer.Use HotBar Function → 读 AC_PlayerInventory.Items[Index]）， 一格滚轮 == 按一次相邻的数字键。
  • 快捷栏指示条一直是空的。 同一个原因：它读的也是那个没人填的数组。 现在改成直接读 AC_PlayerInventory.Items + BP_Farmer.Hot Bar Index， 一个事实源，不留第二本账。

光标与高亮

AC_HighLightComponent 负责「看向即高亮」，WBP_CustomCursor 是自绘光标 —— 它要同时表达三件事：可交互 / 不可交互 / 正在拖拽。 光标在鼠标不动时会轻微呼吸，因为这个游戏的信息密度不低， 玩家很容易忘了自己正拿着东西。

掉落点

松开左键把东西丢回场景时，落点算两段：

/** 鼠标光标射线能打多远（cm） */
float DropTraceDistance = 800.0f;

/** 命中点上再加的固定世界偏移 —— 用户口中的「固定的第三向量」 */
FVector DropLocationOffset = FVector::ZeroVector;

/** 距离相机的硬上限：防止光标射线打空/打到远处墙面时把物品丢到场地外 */
float MaxDropDistance = 400.0f;

先做一次鼠标光标射线拿命中点，再加 DropLocationOffset， 最后用 MaxDropDistance 钳一次 —— 最后这一步是必要的， 不然射线一旦打到很远的墙，物品就会被丢到玩家永远走不到的地方。

输入资产

玩家输入走 Enhanced Input：

资产 作用
IA_LeftClick 主交互：按下抓取/拾取，松开则掉落
IA_RightClick 取消 / 拆解入口（执行链尚未接，见下）
IA_PutIn 倒液：按住把容器里的液体倒进目标
IA_GrapDistance 滚轮推拉抓取物
IA_HotbarScroll 滚轮切快捷栏
IA_Synthesize 拼装固化键

⚠️ 映射上下文要注意活性：固化键必须绑在始终激活的 IMC_Gameplay 上， 不能绑只在拼装模式里加载的 IMC_AssemblySystem —— 否则一退出拼装模式键就失效， 而且不会有任何报错。

目前的进展

  • 三件套接口（BPI_Interactable / BPI_Grabbable / IItemIdentityInterface）
  • AC_InteractionManager 左键分派（装配记录两条路）
  • 统一交互阻断门 IsInteractionBlocked
  • AssemblyItem 碰撞预设（拾取射线 × 拼装吸附正交）
  • 悬停高亮与自绘光标
  • 掉落点（光标射线 + 偏移 + 距离钳制）
  • 滚轮语义分派（世界物体 vs 手部模型）
  • 快捷栏指示条改读真实物品栏
  • 修复左键被「读档」劫持（一次点击触发两次 Load Game）
  • 右键拆解链的执行线接上（节点已有，连线没接）
  • 长按与短按的判定阈值调优

源码

InteractionBlueprintLibrary.h

                // Fill out your copyright notice in the Description page of Project Settings.

#pragma once

#include "CoreMinimal.h"
#include "Kismet/BlueprintFunctionLibrary.h"
#include "GameFramework/Actor.h"
#include "InteractionBlueprintLibrary.generated.h"

class UHotbarManagerComponent;
class UUserWidget;

/**
 * Interaction gating helpers shared by the pickup / grab flows.
 *
 * The click-pickup entry (AC_InteractionManager.TryGrab) calls
 * IsInteractionBlocked as a single early-out so stateful items (a planted
 * flowerpot, chemistry apparatus locked by a running reaction, ...) refuse
 * interaction without every item blueprint having to know about the others.
 */
UCLASS()
class U_TOMATO_API UInteractionBlueprintLibrary : public UBlueprintFunctionLibrary
{
	GENERATED_BODY()

public:
	/**
	 * Whether the actor must refuse click-pickup / grab interactions right now.
	 *
	 * Currently covers:
	 *  1. plantable surfaces (flowerpots etc.) that have living plants —
	 *     locked until the plant is removed (PlantableSurfaceComponent.CurrentPlantCount > 0);
	 *  2. chemistry apparatus belonging to a station whose reaction is
	 *     Processing — locked until the reaction Produces its result.
	 *
	 * Pure query; intended as the single early-out gate at the top of TryGrab.
	 */
	UFUNCTION(BlueprintPure, Category = "Interaction")
	static bool IsInteractionBlocked(AActor* Target);

	/**
	 * The hotbar manager component living on Pawn (null when the pawn has none), exposed as a
	 * BlueprintPure so hand-model flows can reach it without a per-pawn variable getter.
	 *
	 * Used by BP_Farmer.ItemInHand to tell the hotbar which actor it just put in the hand.
	 */
	UFUNCTION(BlueprintPure, Category = "Interaction|Hand")
	static UHotbarManagerComponent* GetHotbarManagerComponent(AActor* Pawn);

	/**
	 * The actor the player is carrying as a HAND MODEL right now - the visual copy spawned by
	 * BP_Farmer.ItemInHand - or null when nothing is in hand.
	 *
	 * SINGLE SOURCE OF TRUTH: UHotbarManagerComponent::EquippedHandActor. ItemInHand calls
	 * NotifyItemEquipped on it right after the model is spawned and grabbed, so every caller -
	 * the hotbar swap chain (OnCenterSlotChanged -> Item In Hand) AND the TryGrab pickup path -
	 * keeps it current.
	 *
	 * Earlier versions also fell back to reflecting BP_Farmer's "Equipped Item" variable for the
	 * pickup path, which called ItemInHand without ever reaching NotifyItemEquipped. That fallback
	 * is gone: if a future flow spawns a hand model without going through ItemInHand it must
	 * update EquippedHandActor too, otherwise the hand counts as "grabbing a world object" and the
	 * hotbar stops switching (see issue 20).
	 */
	static AActor* ResolveHandModelActor(const AActor* Pawn);

	/**
	 * True when the pawn's physics handle is holding a WORLD object driven by the mouse.
	 *
	 * There are two very different things that same handle carries:
	 *   * a world object - a merged assembly, a synthesized result, a loose grabbable
	 *     (AC_AssemblySystem.GrabNewComponent / AC_InteractionManager.TryGrab);
	 *   * the spawned hand model, which ItemInHand also routes through the handle
	 *     (SpawnActor -> SimulatePhysics(true) -> GrabNewComponent) purely so the carried
	 *     item wobbles physically.
	 * Only the first one is a real grab: it is what the mouse wheel pushes / pulls
	 * (AC_AssemblySystem.GrapDistance). Holding the hand model means the wheel belongs to the
	 * hotbar instead, and the hotbar itself must stay switchable.
	 */
	static bool IsGrabbingWorldObjectOnPawn(const AActor* Pawn);

	/**
	 * IsGrabbingWorldObjectOnPawn resolved from a world context object (the player pawn is
	 * looked up through the first player controller), so Blueprint can call it with the
	 * WorldContext pin auto-filled.
	 */
	UFUNCTION(BlueprintPure, Category = "Interaction", meta = (WorldContext = "WorldContextObject"))
	static bool IsGrabbingWorldObject(UObject* WorldContextObject);

	/**
	 * Walk the player's EQUIPPED hotbar slot by SlotDelta (+1 = next slot) and equip whatever that
	 * slot holds, by running exactly the path the number keys run - BP_Farmer."Use HotBar Function",
	 * which reads AC_PlayerInventory."Items"[Index], spawns the hand model through ItemInHand and
	 * stores "Hot Bar Index".
	 *
	 * Why the wheel cannot use UHotbarManagerComponent.HotbarItems: nothing in the project ever
	 * fills that array (WBP_Hotbar only reads it, SetHotbarSlot has no callers), so
	 * OnCenterSlotItemChanged always carries a null item and the scroll path could only ever CLEAR
	 * the hand model - which is exactly the "model disappears and nothing replaces it" bug. The
	 * number-key path is the one that actually knows the items, so the wheel reuses it: one wheel
	 * notch == pressing the next/previous number key.
	 *
	 * The target slot is clamped to the inventory's own item array because Cheak Hotbar indexes
	 * Items[Index] without a bounds check; landing on an empty slot is a no-op (the hand keeps what
	 * it has, it is not emptied). Returns true when an equip was actually requested.
	 */
	UFUNCTION(BlueprintCallable, Category = "Interaction|Hand", meta = (WorldContext = "WorldContextObject"))
	static bool StepHotbarEquip(UObject* WorldContextObject, int32 SlotDelta);

	/**
	 * Rebuild the hotbar strip widget (WBP_Hotbar) straight from the real hotbar data:
	 * AC_PlayerInventory."Items"[0..N-1] plus BP_Farmer."Hot Bar Index".
	 *
	 * WBP_Hotbar used to be fed by UHotbarManagerComponent.HotbarItems - the array nothing in
	 * this project ever fills (see StepHotbarEquip) - so its RefreshHotbarDisplay loop body was
	 * left empty and the strip never displayed anything. The inventory array is what the number
	 * keys and the mouse wheel actually equip from, so the strip reads that instead: one source
	 * of truth, no second bookkeeping array.
	 *
	 * The slots are the Border/TextBlock pairs inside the strip's layout panel, taken in widget
	 * tree order (they are not exposed as widget variables, so they are found by walking the
	 * tree). Slot i shows Items[i], or the slot number when that slot is empty; the slot whose
	 * index equals "Hot Bar Index" is tinted HighlightColor, the others NormalColor.
	 */
	UFUNCTION(BlueprintCallable, Category = "Interaction|Hand")
	static void RefreshHotbarStripFromInventory(UUserWidget* HotbarStrip,
		FLinearColor HighlightColor = FLinearColor(1.0f, 0.72f, 0.15f, 1.0f),
		FLinearColor NormalColor = FLinearColor(0.02f, 0.02f, 0.02f, 0.55f));

	/**
	 * Push the strip refresh into every live hotbar strip widget.
	 *
	 * The strip binds OnHotbarScrolled/OnHotbarSlotUpdated in its own Event Construct, but the HUD
	 * is built while the owning pawn is not resolved yet, so Get Farmer Char Ref returns null,
	 * HotbarManagerRef stays null and BOTH bindings fail silently (verified in PIE: the manager
	 * reports "listeners=NONE" on every equip). Pushing the refresh from the equip path therefore
	 * does not depend on that binding.
	 */
	UFUNCTION(BlueprintCallable, Category = "Interaction|Hand", meta = (WorldContext = "WorldContextObject"))
	static void RefreshAllHotbarStrips(UObject* WorldContextObject);
};
