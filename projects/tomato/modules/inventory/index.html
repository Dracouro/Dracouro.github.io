背包与快捷栏

一块物品结构体、一张物品总表、一套「上手/丢回场景」的往返契约 —— 以及一个没人填的数组造成的连环故障。

进行中C++数据表

一件物品是什么

所有物品都由一张表 + 一个结构体定义。DT_Items 是全场物品的唯一事实源， 行结构 F_ItemInfo 是蓝图 UserDefinedStruct：

字段 说明
ItemID 数字 ID。存档里只存这个数，读档时反查行名
ItemName / 显示名 UI 用
ItemClass 这个物品在场景里生成成什么 Actor
StackSize 堆叠上限
Weight / Rarity 重量与稀有度
ItemType E_ItemType，决定能不能装备等行为
IsContainer? / ToolType 是不是容器、什么相（液体 / 固体）
MaxCapacity / CurrCapacity 容器容量与随手实例变化的当前量
ContentSubstance 容器里装的到底是什么（见倒液与容器）

⚠️ 蓝图 UserDefinedStruct 的成员名带 GUID 后缀（形如 ItemClass_10_D657E8F4...）。C++ 侧用 FindPropertyByName 按裸名去查永远查不到， 必须走 ChildProperties 做前缀匹配。这条不只是 F_ItemInfo， 所有蓝图结构体都这样，所以它被写成了项目级的硬约定 —— 每个新写的反射代码都照抄那段样板。

容器/组件结构

资产 角色
AC_PlayerInventory 玩家背包：Items 数组（按格子）、增删、堆叠、UI 刷新
AC_ItemContainer 通用容器组件：箱子、柜子这类可以共用的容器逻辑
UHotbarManagerComponent 快捷栏：滚轮/数字键切换、持有 EquippedHandActor
AC_GrabComponent / AC_HighLightComponent 抓取与高亮（交互层，见交互系统）

背包侧实现存取的函数是 AddItemByID / RemoveItemByID。 移除这一侧是历史遗留最脏的地方，值得单独讲：

RemoveItemByID 原本的循环会清掉所有行名匹配的格子。 于是「丢掉两件不可堆叠物品中的一件」会把两件一起丢掉。 现在的契约是精确移除 Count 份：C++ 侧的 UFarmingBlueprintLibrary::RemoveItemFromInventory 负责按数量删， 并且顺带跑完蓝图那两条「移除格子 → 刷新 UI」的链， 保证 HUD 图标与快捷栏的装备状态跟数组同步 —— 只改数组不改 UI， 就会出现「背包里没了但图标还在」这种第三人称视角才看得见的 bug。

已知残留：RemoveItemByID 的减法节点方向仍然是反的 （只在「多堆移除」时触发，单件不受影响）；AddItemByID 每次会打一条 Divide-by-zero 警告。两者都不阻塞当前闭环，但都记着。

上手与丢回场景

物品在游戏里有三个位置：背包 → 手上 → 场景。两个方向都要走通：

背包 → 手上   BP_Farmer.ItemInHand(Class)
                └ 清掉旧手部模型 → 按类生成新 Actor（缩放 ItemHeldScale）
                └ 关碰撞 → 交给物理手柄抓住（为了让它在手里晃）
                └ 通知 UHotbarManagerComponent.NotifyItemEquipped → EquippedHandActor

手上 → 场景   UFarmingManagerComponent.DropEquippedItemToWorld(item, transform, count)
                └ 在鼠标光标射线命中点 + DropLocationOffset 生成一个世界副本
                └ 从背包移除 Count 份 → 销毁手上那份

⚠️ 「手部模型」也是被物理手柄抓着的 —— 这一点是很多手感 bug 的根源。 它跟「场景里抓着一个合并体」用的是同一套手柄机制， 所以任何「手柄在干嘛」的判断都必须先区分这两者 （见交互系统的 IsGrabbingWorldObjectOnPawn）。 另外有一条双重销毁契约：DropEquippedItemFromHand 已经负责销毁手上那份， TryGrab 的掉落分支不许再销毁同一个 Actor。

快捷栏：一个没人填的数组

快捷栏坏过一串 bug，最后追到同一个根因：

UHotbarManagerComponent.HotbarItems 这个数组工程里没有任何地方往里写过东西 —— 只有 UI 在读它。所以以它为数据源的路径全都表现为「东西消失」： 滚轮切栏 = 先清空手上、再装上空的；快捷栏指示条 = 永远空白。

修法不是「补上写数组的逻辑」（那会变成两本账，迟早再漂）， 而是让所有路径统一读真实物品栏：

功能 改后读什么
滚动切栏 复用数字键那条路（AC_PlayerInventory.Items[Index] + Use HotBar Function）
快捷栏指示条 AC_PlayerInventory.Items + BP_Farmer.Hot Bar Index，高亮当前格

索引做了钳制，因为 Cheak Hotbar 读 Items[Index] 时没有边界检查； 落在空格上是 no-op（手里保持原样，而不是被清空）。

存档

背包与快捷栏的存档结构刻意做得很小 —— 只存「能反查回去的最小信息」：

USTRUCT(BlueprintType)
struct FInventorySlotSaveData
{
    int32 ItemID = 0;          // 反查 DT_Items 行名
    int32 Quantity = 1;
    int32 CurrCapacity = -1;   // -1 = 未设（老存档 / 非容器），读取时保留行默认值
    uint8 ChemicalContent = 0; // 0/None = 未覆盖，读取时按行的默认内容
};

USTRUCT(BlueprintType)
struct FHotbarSlotSaveData
{
    int32 SlotIndex = 0;
    FName ItemRowName = NAME_None;   // 按行名而不是指针存
};

-1 和 0 在这里是「未设」的哨兵值，不是「空」。 这个约定的价值在于向前兼容：老存档里没有这两个字段， 读出来就是 -1 / 0，加载器于是保留表里的默认值，而不是把容器清空。 写存档的人只要不主动写哨兵值进去，兼容性就是自动的。

美术与实装状态

物品规划是 120 种垃圾，但正式资产还没齐：

  • 表结构、行名（Junk_*）与外观描述已经全部定稿，在 docs/ 的垃圾总表与 生成物美术资产表里；
  • 正式 DT_Items 行、以及每件垃圾的独立网格仍需要美术侧产出， 拼装固化的「正式配方」也就卡在这一步（目前只有测试配方）。

另外表里还留着一些拼写残留（Cheak Hotbar / Init Grap Offset / Get Inventory Weget / WBP_Hatbar / Dequipe Item）， 属于能用但碍眼的一类，改之前要连带把引用它的蓝图一起改。

源码

InventorySaveData.h

                // Fill out your copyright notice in the Description page of Project Settings.

#pragma once

#include "CoreMinimal.h"
#include "InventorySaveData.generated.h"

/** Serialized representation of one inventory slot. */
USTRUCT(BlueprintType)
struct FInventorySlotSaveData
{
	GENERATED_BODY()

	/** Numeric item ID from F_ItemInfo.ItemID. Reverse-looked up in DT_Items during load. */
	UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Save")
	int32 ItemID = 0;

	/** Stack count for this slot. */
	UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Save")
	int32 Quantity = 1;

	/**
	 * Per-instance container fill (F_ItemInfo.CurrCapacity). -1 = unset
	 * (old saves / non-containers) — the loader then keeps the row default.
	 */
	UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Save")
	int32 CurrCapacity = -1;

	/**
	 * Per-instance chemical content override (EChemicalSubstance). 0/None =
	 * unset (old saves / plain water containers) — the loader then keeps the
	 * row-derived content.
	 */
	UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Save")
	uint8 ChemicalContent = 0;
};

/** Serialized representation of one hotbar slot. */
USTRUCT(BlueprintType)
struct FHotbarSlotSaveData
{
	GENERATED_BODY()

	/** Slot index (0..NumVisibleSlots-1). */
	UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Save")
	int32 SlotIndex = 0;

	/** DT_Items row key identifying the item in this slot, or None if empty. */
	UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Save")
	FName ItemRowName = NAME_None;
};
