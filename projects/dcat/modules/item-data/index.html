物品数据

三个枚举、三个结构体、两张表 —— 以及一次做到一半的迁移：新结构体丢掉了旧结构体的两个字段、补上了两个新字段，而那张新表里一行数据都没有。

搁置蓝图数据表结构体

三个枚举

/Game/Inventory/Blueprints/Enums/ 下三个枚举，取值都读出来了：

枚举 取值
E_ItemType Resource、Equipable、Armor、Consumable、Buildable
E_ItemRarity Common、Uncommon、Rare、Epic、Legendary
E_ArmorType Helmet、Chest、Pants、Boots

⚠️ 一个只有深入资产才能看到的事：这三个枚举的内部枚举名全是 NewEnumerator0 / NewEnumerator1 / …，作者只改了“显示名”， 没有改“条目名”。在蓝图里点选时看到的是 Resource、Common 这些， 但序列化出来、写在数据表里、以及在 C++ 侧引用的，都是 NewEnumeratorN。 这类“显示名与内部名不一致”在纯蓝图项目里能跑， 但一旦要迁移到 C++ 或者做外部工具对接，就得重新对一遍。

E_ItemType 的取值顺便透露了设计野心：Equipable（可装备）、Armor（护甲）、 Buildable（可建造）—— 都建好了，但表里没有一行用到它们 （两行的 ItemType 都是 Resource）。

三个结构体

结构体 字段数 用途
F_ItemStruct 15 物品定义（Item_Data 的行结构）
F_SlotStruct 2 背包槽：ItemID + Quantity
S_ItemInfo 15 另一套物品定义（ItemInfo_Data 的行结构）

F_SlotStruct 只有两个字段，这是“槽 = (什么东西, 几个)“的最简表达：

字段 类型 说明
ItemID Name ⚠️ 是 Name 不是 int，也不是行句柄
Quantity int 数量

F_SlotStruct 的 ItemID 用 Name 存 —— 所以槽与物品表之间是靠“名字相等”关联的（FindSlot 里是 EqualEqual_NameName），而不是靠 DataTableRowHandle。 这和 ItemDataComponent.ItemID（是 DataTableRowHandle）形式不同 —— 同一份工程设计里，物品引用有两种不同的引用方式，见下面那张对照表。

两张表：一张有两个字段名带问号，另一张一行数据都没有

Item_Data ← F_ItemStruct

15 列，2 行：

行 ItemName Description ItemClass StackSize Thumbnail
Text 测试物品 测试物品 BP_Testltem_C 100 T_Ceramic_Tile_M
Apple 苹果 又大又红的苹果 BP_Apple_C 10 Tex_seeds_10_b

其余的列两行填的完全一样，而且是这样的值：

列 两行的值
ItemDamage 0
ItemRarity Common
ItemCurHP / ItemMaxHP 0 / 0
IsStackable? false
ItemType Resource
ArmorType Helmet
UseAmmo? / CurrAmmo / MaxAmmo false / 0 / 0

两个明显的矛盾：

  1. 苹果的 ArmorType 是 Helmet（头盔）。因为表是复制粘贴出来的， 作者没把不适用的枚举列清掉 —— 它读起来像“苹果是顶头盔”。
  2. IsStackable? 是 false，但 StackSize 一个有 100、一个有 10。 “不可堆叠”和“堆叠上限 10”是互相打架的。 FindSlot 判断“能不能再塞”时读的是 Get Max STack Size（走 StackSize）， 所以实际生效的是 StackSize，IsStackable? 这列填了但没查到被谁读过。

这两处都不是 bug（不崩、不报错），而是表在填的时候没被认真对待。 这也是“数据驱动的原型”最常见的形态：结构体一次建全，值先随便填。

ItemInfo_Data ← S_ItemInfo

15 列，0 行。

表建好了、列接好了、引用了 S_ItemInfo —— 但里面一行数据都没有。

一次做到一半的迁移

把两个 15 字段结构体逐列对齐，差集非常清楚：

F_ItemStruct S_ItemInfo 说明
ItemName ItemName 共有
Description Description 共有
Thumbnail Thumbnail 共有
ItemClass ItemClass 共有
StackSize StackSize 共有
ItemDamage ItemDamage 共有
ItemRarity ItemRarity 共有
ItemCurHP ItemCurHP 共有
IsStackable? IsStackable? 共有
ItemType ItemType 共有
UseAmmo? UseAmmo? 共有
CurrAmmo CurrAmmo 共有
MaxAmmo MaxAmmo 共有
ItemMaxHP — ❌ 被删了
ArmorType — ❌ 被删了
— ItemID ✅ 新加的
— ItemQuantity ✅ 新加的

11 + 4 = 15，两边对上。翻译成人话：

S_ItemInfo = F_ItemStruct 减掉 ItemMaxHP 和 ArmorType， 加上 ItemID 和 ItemQuantity。

这是一次有意为之的重新设计，方向也很清楚：

  • 减掉的两项都是“装备/护甲”专用的（最大生命、护甲部位）—— 说明作者想把“消耗品/资源”和“装备”分开，不再让苹果也带着头盔字段。
  • 加上 ItemID 是关键：旧结构体里“物品 ID”只能靠数据表的行名充当， 新结构体把它变成结构体自己的字段。
  • 加上 ItemQuantity 是把“数量”从背包槽搬进物品定义里。

但这次迁移只做了一半：

迁移动作 做了吗
建新结构体 S_ItemInfo ✅
建新数据表 ItemInfo_Data ✅ 表结构齐
往新表里填数据 ❌ 0 行
把读写点改到新结构体 ❌ InventorySystem / 背包槽 用的仍是旧的那套

所以现在工程里有两条并行的数据线，而只有旧的那条是活的。

谁引用了谁

结构体 被谁引用
F_ItemStruct Item_Data（表）、InventorySystem、BP_ThirdPersonCharacter、W_DragPreview、W_InventorySlot
F_SlotStruct InventorySystem、W_PlayerMenu、W_InventoryGrid
S_ItemInfo ItemInfo_Data（空表）、BPC_ItemContainer（从未被使用的容器）、BP_ThirdPersonCharacter

这张表把事情说得很明白：

  • F_ItemStruct 有 5 个引用者，其中 4 个是活的（表 + 逻辑 + 两个 UMG）—— 它是当前真正在用的物品结构。
  • S_ItemInfo 的 3 个引用者，一个是空表、一个是死类， 只剩 BP_ThirdPersonCharacter 一个活引用 —— 而且角色侧也没有实际读写它（只是作为类型引用挂在变量上）。
  • F_SlotStruct 只被背包和两个 UMG 引用，正好对应“槽”的三角关系： 容器持有一份、菜单显示一份、网格显示一份。

另外注意：BP_ThirdPersonCharacter（模板角色，BP_CATTTTTT 的父类） 同时引用了新旧两个物品结构体 —— 这是迁移留下的另一个指纹： 改动是顺手在模板角色上动的，而模板角色是猫的父类。

数据是怎么被读出来的

全工程读配置表的入口只有一个：

InventorySystem.GetItemData（3 节点）
  FunctionEntry → GetDataTableRow(Item_Data) → FunctionResult

一个 GetDataTableRow 节点，就完了。 所有物品属性 （名字、描述、堆叠上限、缩略图）都从这一个函数出来， 再由 AddToInventory / FindSlot / UMG 各自取用。

这个设计是干净的 —— 数据访问收敛在单一入口。 问题不在读取方式，而在表里没有内容。
