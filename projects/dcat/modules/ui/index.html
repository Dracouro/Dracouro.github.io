五个真正在干活的控件

W_PlayerHUD：一个菜单宿主

它自己的控件树几乎是空的（就一个 CanvasPanel），因为子界面都是运行时创建的：

CustomEvent DisplayPlayerMenu  → CreateWidget → Set Menu      → AddToViewport
CustomEvent DisplayBoxMenu     → CreateWidget(BoxInventorySystem) → Set Menu → AddToViewport
CustomEvent DisplayActionMenu  → CreateWidget(InventorySystem, Index) → Set ActionMenu → AddToViewport
（外加一个 RemoveFromParent 的收尾分支）

三个 CustomEvent 的入参和三个子控件的自建变量完全对得上， 所以对应关系是可以确证的：

宿主事件 创建的子控件 依据
DisplayBoxMenu W_BoxInventory CreateWidget 带 BoxInventorySystem 参数，而 W_BoxInventory 正好有同名变量
DisplayActionMenu W_ActionMenu 带 InventorySystem + Index，W_ActionMenu 正好有这两个变量
DisplayPlayerMenu W_PlayerMenu 无参数，W_PlayerMenu 的变量是两个位置结构体

两个 UMG 变量 Menu（当前菜单）与 ActionMenu（当前右键菜单）分开存 —— 说明“右键菜单”和“主菜单”是要同时存在的，刷新时各管各的。

W_InventoryGrid：遍历槽位建子项

PreConstruct:
  Content（读）→ ForEachLoop → BreakStruct(F_SlotStruct)
    → CreateWidget(W_InventorySlot)  ← 传 ItemID / Quantity / InventorySystem / ContentIndex
    → BOX_Grid.AddChild

CustomEvent DisplayInventory(InventorySystem):
  Set InventorySystem → BOX_Grid.ClearChildren
  → Bind Event to Onlnventoryupdate → CustomEvent UpdateInventory → ClearChildren
  • WrapBox 作为容器 —— BOX_Grid 是 WrapBox，所以槽位满了会自动换行。 外面套 ScrollBox 提供滚动，最外层 Border 给边框。
  • 刷新策略是“全清重建”：UpdateInventory 里只有一句 ClearChildren， 然后靠 PreConstruct / DisplayInventory 重新生成全部子项。 对 20 来个槽位没问题，槽位多了会有明显开销。
  • 绑定的是 Onlnventoryupdate 委托 —— 也就是背包系统 里那个拼错名的多播委托。UI 刷新完全靠它驱动，没有轮询。

W_InventorySlot：一格里做的事最多

PreConstruct:
  ItemID（name）→ Get Data Table Row(Item_Data) → BreakStruct(F_ItemStruct)
    → IMG_Icon.SetBrushFromTexture(Thumbnail)
    → TXT_Quantity.SetText(Quantity)
    → 按数量 / 有无图标切换 SetVisibility（两次）
    → CreateWidget(W_ItemInfo) 传 Thumbnail / Name / Description / Quantity
    → SetToolTipWidget          ← ★ 把 W_ItemInfo 当 tooltip

两个要点：

  1. 格子里直接查数据表（GetDataTableRow(Item_Data)）， 这是物品数据那条唯一入口之外的第二处读表点 —— UI 没有通过 GetItemData 函数绕一圈，而是自己读。 两处读法并存，说明 GetItemData 这个“统一入口”其实并没有被统一使用。
  2. W_ItemInfo 是 W_InventorySlot 的 tooltip —— 由 SetToolTipWidget 挂上去。这解释了为什么 W_ItemInfo 自己图是空的： 它只负责显示，数据全靠 CreateWidget 时传进来的四个变量。

顺带：这个控件的按钮叫 BTN_SlotButon（Buton 少一个 t）。 这是本工程第 N 处拼写问题 —— 已经不值得逐个数了。

W_BoxInventory 与 W_PlayerMenu：同一套模式

两个都是“打开界面 → 铺数据 → 把输入交给 UI”，写法几乎一样：

Construct:
  GetPlayerCharacter → GetComponentByClass
    → BagGrid.DisplayInventory(InventorySystem)
    → BoxGrid.DisplayInventory(BoxInventorySystem)      ← 箱子是两个网格
  SetInputMode(UI Only) + bShowMouseCursor = true

Destruct:
  SetInputMode(Game Only) + bShowMouseCursor = false
  • W_BoxInventory 同时铺两个网格：左边玩家的 InventorySystem、右边箱子的 BoxInventorySystem。所以箱子界面是“两栏对拖”的形态。
  • 用 Construct / Destruct 而不是 BeginPlay —— 说明是按“打开时构建、 关闭时销毁”来管理的，配合 W_PlayerHUD 的 AddToViewport / RemoveFromParent。
  • ⚠️ bShowMouseCursor 的赋值和 SetInputMode 都在 UI 里做 —— 输入模式本该是 PlayerController 的职责，和 增强输入里“IMC 被组件挂载”是同一类越界。

W_ActionMenu：三个按钮共用一个函数

Construct:    GetMousePositionOnViewport → SlotAsCanvasSlot → SetPosition  ← 菜单在鼠标处弹出
OnMouseLeave: RemoveFromParent                                            ← 鼠标移开就关
Tick:         RemoveFromParent

三个 ComponentBoundEvent（BTN_Use / BTN_DropOne / BTN_DropAll）
   → 各自读 InventorySystem + Index
   → 都调 ServerRemoveFromlnventory

三个按钮调的是同一个函数，靠参数区分意图。这个函数的引脚签名读出来了：

ServerRemoveFromlnventory(Index, RemoveWholeStack, IsConsumed)

于是三个按钮的对应关系基本能推出来：

按钮 文案 大概传的参数
BTN_Use 使用 IsConsumed = true
BTN_DropOne 丢弃1个 RemoveWholeStack = false
BTN_DropAll 丢弃全部 RemoveWholeStack = true

⚠️ 但这些参数的值仍然是引脚常量、读不到（下面那张表里的三个按钮 确实是三份独立的 ServerRemoveFromlnventory 节点，所以值必然不同， 但“哪一个传哪个”是推断）。

更要紧的是：ServerRemoveFromlnventory 在 InventorySystem 里是空函数 （见背包系统）—— 所以这三个按钮现在按下去什么都不会发生。 界面做完了、参数接对了、被执行的那一端还没写。

三个图是空的控件

控件 控件树 图 判断
W_Hotbar 完整的 8 格数字栏 只有 PreConstruct/Construct/Tick 三个空事件 纯静态 —— 8 格永远是 1–8
W_ItemInfo 名字/描述/数量/图 四行齐全 三个空事件 纯展示 —— 数据从变量来，符合设计
W_Inventory 两套页签容器 三个空事件 只有骨架 —— 页签按钮没有绑定事件

W_Hotbar 值得单独说一句：UniformGridPanel 里排了 8 个格、 每格一个 Border + 一个 TextBlock（1–8），控件做得挺完整， 但一行逻辑都没有 —— 没有读背包、没有高亮当前格、没有快捷键响应。 它和 W_Inventory 的 Crafting 页签属于同一类： 界面先搭好了，功能没接上。
