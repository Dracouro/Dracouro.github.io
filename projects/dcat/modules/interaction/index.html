交互与高亮

一个接口、三个函数、四处实现，而四处实现彼此都不一样 —— 真正干活的是挂在物品上的两个组件，物品 Actor 自己反倒是个空壳。至于描边，查到最后发现只写了"关"、没写"开"。

搁置蓝图蓝图接口组件

接口只有三个函数

Interactlnterface 是一个蓝图接口，声明了三个函数 —— 图里加起来只有 4 个节点。 引脚逐个读出来之后，签名是这样的：

函数 签名（从引脚读） 备注
LookAt LookAt() → Message: text 无参，返回一段文本
InteractWith InteractWith(PlayerCharacter: BP_ThirdPersonCharacter_C) 把“谁来交互”传进来
UnLook UnLook() 无参无返回

⚠️ 这份签名里藏着一个没做完的设计： LookAt 是唯一一个有返回值的函数，返回类型是 text。 按意图很好猜 —— 「看向某物时，让它回一句提示文字」（比如“按 E 拾取”）。 而界面里确实没有一个交互提示控件， HighLightComponent 也根本没实现 LookAt。 也就是说：这条提示文字的链路，从接口声明之后就没有下文了。 调用点上那个 LookAt 消息节点的返回值引脚是空接的。

⚠️ Interactlnterface —— 又是 l / I 那一类问题（本意 InteractInterface）。 这是本工程第五处了。这个错名字已经扩散到 4 个蓝图（接口本身 + 三个实现者）。 更麻烦的是：蓝图接口的资产名一旦生成，改名会连带改所有实现者的接口引用 —— 所以它几乎注定要一直错下去。

顺带一个有意思的对比：InteractWith 的参数类型写作 BP_ThirdPersonCharacter_C，而不是 BP_CATTTTTT_C。 接口是照着模板角色声明的 —— 又一个“从模板长出来”的指纹。

四种实现，四种状态

接口有四个实现者，没有一个写法是相同的：

实现者 自建图 接口实现情况
ItemDataComponent EventGraph 15 节点 ✅ InteractWith 有实质逻辑；UnLook 空
HighLightComponent EventGraph 6 节点 ⚠️ 只实现了 UnLook；InteractWith 空；LookAt 没实现
BP_Box EventGraph 9 节点 ✅ InteractWith 打开箱子菜单；UnLook 空
BP_Testltem EventGraph 3 节点（全空） ⚠️ 三个函数都是空实现
BP_Apple EventGraph 6 节点（全是 CallParentFunction） ⚠️ 纯转发

BP_Testltem 是个空壳

它对接口的“实现”是：EventGraph 里只有三个空事件 （ReceiveBeginPlay / ReceiveActorBeginOverlap / ReceiveTick）， 接口的 InteractWith / UnLook 只有 ubergraph 入口、没有节点。

也就是说 BP_Testltem 自己按 E 什么都不会发生。 它作为物品的价值全在它挂的两个组件上（见下）。

BP_Apple 是空壳的空壳

BP_Apple 继承 BP_Testltem，自建 0 变量、0 新逻辑， 六个节点就是把三个事件 + UserConstructionScript 各转发给父类一次：

ReceiveBeginPlay        → CallParentFunction(ReceiveBeginPlay)
ReceiveActorBeginOverlap→ CallParentFunction(ReceiveActorBeginOverlap)
ReceiveTick             → CallParentFunction(ReceiveTick)
UserConstructionScript  → CallParentFunction(UserConstructionScript)

那它为什么存在？因为它要当 Item_Data 表里 Apple 那一行的 ItemClass。 两张表的 ItemClass 列指向的是 BP_Testltem_C（Text 行）与 BP_Apple_C（Apple 行）—— 一个物品一行的 Class 字段，需要一个能区分的类。 所以 BP_Apple 的唯一职责是“有个不同的类名”， 里面一行逻辑都没有（连网格都没换，见下）。

物品的“配方”：一个默认立方体 + 两个组件

BP_Testltem 的组件树只有四个节点，但信息量很大：

BP_Testltem (Actor)
├─ DefaultSceneRoot
├─ Cube            (StaticMeshComponent)  ← 网格是 /Engine/BasicShapes/Cube
├─ ItemDataComponent  (ItemDataComponent_C)     ← 拾取
└─ HighLightComponent (HighLightComponent_C)    ← 描边
  • 网格就是引擎自带的 Cube（/Engine/BasicShapes/Cube.Cube）， 相对缩放 0.75。物品连个像样的模型都还没换 —— Item_Data 表里两行都填了缩略图，但场景里的实物是方块。
  • BP_Apple 继承之后没有加任何组件、也没换网格， 所以现在“苹果”和“测试物品”在世界里长得一模一样，都是立方体。

BP_Box 是唯一在 Actor 层写了逻辑的

Event InteractWith
  → GetPlayerController → DynamicCast(PC_MyPlayerController_C)
  → HUD（读）+ InventorySystem（读）
  → DisplayBoxMenu

按 E 打开箱子界面。 BP_Box 自己的组件是：

BP_Box (Actor)
├─ DefaultSceneRoot
├─ StaticMesh
├─ InventorySystem    ← ★ 箱子用的是普通的 InventorySystem 组件
└─ HighLightComponent

⚠️ 注意箱子上挂的是 InventorySystem，不是那个专门写来做容器的 BPC_ItemContainer —— 后者从头到尾没被挂到任何东西上 （详见背包系统）。 而且 BP_Box 上没有 ItemDataComponent， 所以“能不能捡箱子”这件事在组件层面是不成立的 —— 箱子只能“开”，不能“捡”。

拾取的完整链路

把三处代码串起来，一次按 E 是这样走的：

① InventorySystem.InteractionTrace（每帧）
     GetPlayerCameraManager → SphereTraceSingle（通道见下）
     命中 → BreakHitResult → 取到 Actor
     新旧不同 → 对旧的发 UnLook 消息 / 对新的发 LookAt 消息

② InventorySystem.EventGraph
     EnhancedInputAction(IA_Interact) → GetOwner → Server_Interact
     → DynamicCast → OnLocalInteract → GetComponentByClass
     → Message InteractWith   ← 发给组件，不是发给 Actor

③ ItemDataComponent.EventGraph
     Event InteractWith
       → InventorySystem（读自己的引用）→ IsValid 宏
       → ItemID（DataTableRowHandle）→ BreakStruct
       → Quantity（int）
       → AddToInventory
       → IfThenElse → GetOwner → K2_DestroyActor   ← 场景里那份自己消失

三个要点：

  1. 接口消息是发给“组件”的（GetComponentByClass 之后才 Message）—— 这解释了为什么 BP_Testltem 自己的空实现不影响拾取： 真正响应的是挂在它身上的 ItemDataComponent。
  2. ItemID 是 DataTableRowHandle 类型，所以要 BreakStruct 才能取出 行名与行结构；Quantity 是组件上的独立 int。
  3. 拾取后 K2_DestroyActor 销毁的是 GetOwner() —— 组件把宿主 Actor 干掉。数据已经先 AddToInventory 了，所以顺序是对的。

顺带一个组件级的细节：ItemDataComponent 的 ReceiveBeginPlay 里 调了一次 SetReplicates（取 GetOwner 再设）—— 和背包系统里那批空 Server_* 函数是同一个意图： 联网是规划过的。但物品拾取是纯本地实现的， 客户端销毁 Actor 在联机下会与服务器状态打架。

高亮：只写了“关”，没写“开”

这是本模块最值得记的一处。HighLightComponent 的 EventGraph 只有六个节点：

Event UnLook
  → GetOwner
  → GetComponentByClass
  → SetRenderCustomDepth(false)

SetRenderCustomDepth 这个调用，在全工程（所有蓝图、所有图）里只出现这一次。

而物品的网格组件默认值是：

Cube (StaticMeshComponent)
  bRenderCustomDepth       = False
  CustomDepthStencilValue  = 0

也就是说：

  • 物品网格出生时就是不写深度缓冲的；
  • HighLightComponent 实现了 LookAt 吗？没有 —— 它的图里只有 ReceiveBeginPlay / ReceiveTick / UnLook 三个事件；
  • 所以**“把描边打开”这半边的代码不存在**。

结论：目前实机里物品不会有描边。 UnLook 里那行 SetRenderCustomDepth(false) 是把一个本来就是 false 的值又设成 false。

这是个很典型的“做到一半”的痕迹：接口的三个函数齐了、 追踪射线也发了 LookAt 消息、组件也挂上了、只有最后那一个布尔没写。 补上它只需要在 LookAt 事件里加一句 SetRenderCustomDepth(true)。

追踪通道：自定义的 Interactive

射线用的通道不是 Visibility 也不是 Camera，而是工程里唯一一条自定义通道：

+DefaultChannelResponses=(Channel=ECC_GameTraceChannel1,DefaultResponse=ECR_Ignore,
                         bTraceType=True,bStaticObject=False,Name="Interactive")

ECC_GameTraceChannel1 = 名为 Interactive 的追踪通道， 默认响应是 ECR_Ignore —— 谁都不响应，除非物品主动声明“我在这条通道上可被命中”。

这个设计是对的：追逐射线不会撞到墙、地形、玩家 —— 只有物品会挡它，所以“看向什么”的结果天然就是一串候选物品。 代价是：新加一种可交互物时，忘了设置 Interactive 响应就会静默失效， 不会有任何报错。

具体是哪个组件、哪个插槽声明了 Interactive 响应， 从组件默认值里读不到（碰撞配置不在 obj dump 的输出范围）。 这点只能到编辑器里核对。
